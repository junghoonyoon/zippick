# 재개발이 옆 단지 값에 주는 영향 — 분석 설계서

작성일 2026-08-08 · 대상 코드 `pipeline/redevelopment_analysis.py`

---

## 1. 무엇을 알아내려는가

지금 집픽은 **"근처에 정비사업이 있으면 점수를 올린다/내린다"** 를 사람이 정한
숫자로 계산한다. 이 설계서는 그 숫자를 **실거래로 검증하고 다시 맞추기 위한**
분석 절차를 정한다.

답해야 할 질문은 네 가지다.

1. 정비사업 근처 구축 아파트는 정말 더 오르는가?
2. 얼마나 가까워야 효과가 있는가? (거리)
3. 사업의 어느 단계에서 값이 움직이는가? (시점)
4. 매매와 전세 중 무엇이 먼저 움직이는가? (선행 지표)

## 2. 먼저 고칠 것 — 현재 코드에서 확인된 문제

분석을 돌리기 전에 아래 네 가지를 고쳐야 한다. **지금 상태로는 분석 결과를
코드에 반영할 자리가 없다.**

### 문제 ① 가장 중요한 단계가 한 건도 안 잡힌다

`STAGES`에는 `이주·철거`와 `입주 예정`이 있지만, 실제로 분류되는 구역은 **0건**이다.
원본 데이터의 단계값(`stage`)에 "이주", "철거", "입주 예정"이라는 글자가
아예 없기 때문이다.

| 단계 | 분류된 구역 수 |
|---|---|
| 조합설립인가 | 786 |
| 검토·후보지 | 326 |
| 사업시행인가 | 156 |
| 착공 | 109 |
| 정비구역 지정 | 89 |
| 관리처분인가 | 83 |
| **이주·철거** | **0** |
| **입주 예정** | **0** |

전세값이 가장 크게 움직이는 구간이 **이주 단계**인데, 그 단계를 잡아내지 못한다.

### 문제 ② 신속통합기획 225곳이 통째로 빠진다

`_project_type()`이 "신속통합기획"을 어떤 유형으로도 인식하지 못해 `None`을
돌려주고, 그대로 걸러진다. 전체 2,585곳 중 **1,036곳이 점수 계산에서 제외**된다.
지도 화면 원칙(`AGENTS.md`)에서는 신속통합기획을 우선 표시하라고 해놓고,
점수에서는 빠지는 모순이 있다.

### 문제 ③ 공급 부담 감점이 절대 작동하지 않는다

```python
if large_supply >= 3000:
    score -= 12
```

`plannedHouseholds` 값을 가진 구역은 **0건**이다. `large_supply`는 항상 0이므로
이 조건은 한 번도 참이 되지 않는다. 즉 "새 아파트가 대량으로 쏟아지는 부담"은
점수에 반영된 적이 없다.

### 문제 ④ 단계가 한 칸씩 앞당겨져 있다

`조합설립인가 추진중(연번부여)` 491곳이 `조합설립인가`로 분류된다. **추진 중인데
인가받은 것으로 계산**된다. `건축심의`(125곳)는 조합설립 이후 단계인데
`검토·후보지`로 떨어져 오히려 감점(-5)을 받는다.

**이 파일이 없으면 분석 자체가 불가능하다.** 구역이 각 단계에 **언제** 들어갔는지가
있어야 "그 시점 전후"를 비교할 수 있다.

```csv
zoneId,zoneName,stage,eventDate,plannedHouseholds,source
11000UQ...,노량진1,관리처분인가,2026-04,3103,서울시고시
11000UQ...,노량진1,이주·철거,2026-07,3103,조합공지
```

확보 경로는 세 가지다.

1. **서울시 정비사업 정보몽땅** — 구역별 고시일자 공개. 1순위.
2. **각 구청 고시·공고 게시판** — 관리처분인가 고시일. 보완용.
3. 위 둘로 안 되는 구역은 **분석 대상에서 제외**한다. 추정으로 채우지 않는다.

세대수(`plannedHouseholds`)도 이때 같이 채운다.

## 4. 분석 설계

### 4-1. 분석 단위

- **단지 × 평형대 × 월** 단위로 집계한다. 같은 단지라도 25평과 33평은 따로 본다.
- 가격은 **월별 중위 평당가(만원/3.3㎡)** 를 쓴다. 평균은 이상거래에 흔들린다.
- 그 달 거래가 **3건 미만이면 결측 처리**한다. 억지로 채우지 않는다.
- **호가는 쓰지 않는다.** 집픽은 실거래만 보유한다.

### 4-2. 1단계 — 이벤트 스터디 (단계별 반응 시점 찾기)

각 정비구역의 단계 진입 시점을 기준점 `T=0`으로 잡고, 주변 단지의
가격 경로를 겹쳐 본다.

- **관측 구간**: `T-24개월 ~ T+24개월`
- **거리 밴드**: `0~500m` / `500m~1km` / `1~2km` / `2~3km`(대조군 후보)
- **대상 단계**: 정비구역 지정 / 사업시행인가 / 관리처분인가 / **이주·철거** / 착공 / 입주
- **출력**: 밴드 × 단계별 누적 초과수익률 곡선 (매매·전세 각각)

여기서 확인할 것: **거리가 멀어질수록 효과가 줄어드는가**, 그리고
**전세 곡선이 매매 곡선보다 앞서 꺾이는가**.

### 4-3. 2단계 — 이중차분 (효과 크기 추정)

이벤트 스터디로 눈에 보이는 패턴을 숫자로 확정한다.

```
log(평당가) = α + β₁·(가까움) + β₂·(사건이후) + β₃·(가까움 × 사건이후)
              + 단지고정효과 + 월고정효과 + ε
```

- **처리군**: 구역 경계에서 500m 이내 단지
- **대조군**: 같은 자치구 안, 2~3km 밴드 단지
- **β₃** 가 우리가 원하는 값이다 — "재개발 때문에 추가로 오른 폭"
- 단계별로 따로 추정해 **단계별 계수표**를 만든다
- 표준오차는 **자치구 단위로 클러스터링**한다

### 4-4. 3단계 — 공급 부담 검증

입주 시점 전후로 **세대수 구간별**(1,000 미만 / 1,000~3,000 / 3,000 이상)
나눠 같은 회귀를 돌린다. 지금 코드의 `-12점` 감점이 타당한지, 임계값이
3,000이 맞는지를 여기서 확인한다.

## 5. 결과를 코드에 반영하는 형태

하드코딩된 상수를 **설정 파일로 빼고**, 분석 결과값을 넣는다.

    "사업시행인가":   { "sale": null, "jeonse": null, "n": null, "pValue": null },

반영 규칙 세 가지.

1. **통계적으로 유의하지 않은(p ≥ 0.05) 단계는 가중치 0**으로 둔다. 점수를
   움직이지 않는다.
2. **관측치가 30개 미만인 칸은 `null`** 로 두고, 화면에서는 "데이터가 부족해요"로

3. 사용자 화면에는 **"근처 재개발로 최근 3년간 비슷한 단지보다 평균 N% 더
   올랐어요"** 처럼 근거가 붙은 문장으로 쓴다. 미래 가격을 단정하지 않는다.

## 7. 검증 방법

분석 결과를 믿어도 되는지 확인하는 절차다. 이 중 하나라도 실패하면 반영하지 않는다.

1. **평행추세 검정** — 사건 이전 24개월 동안 처리군과 대조군의 가격 흐름이
   비슷했는가. 사건 전부터 이미 벌어져 있었다면 재개발 효과가 아니다.
2. **가짜 사건 검정** — 사건일을 실제보다 24개월 앞당겨 같은 회귀를 돌린다.
   여기서도 효과가 나오면 모형이 잘못된 것이다.
3. **대조군 바꿔보기** — 대조군을 2~3km 대신 인접 자치구로 바꿔도 계수 부호와
   크기가 유지되는가.
4. **사례 대조** — 노량진뉴타운·대방대림처럼 이미 알고 있는 사례에 모형을
   적용해 실제 실거래 흐름과 맞는지 눈으로 확인한다.
5. **회귀 테스트** — 기존 단지 점수가 얼마나 바뀌는지 diff를 뽑는다. 상위 100개
   단지의 순위가 크게 뒤집히면 원인을 먼저 설명한다.

## 8. 한계 — 미리 밝혀둘 것

- **정비사업만으로 값이 움직이지 않는다.** 대방대림만 해도 신안산선 대림삼거리역
  (2027년 개통 예정)과 신길뉴타운 완성이 노량진뉴타운보다 더 직접적인 변수다.
  역 개통, 학군, 금리, 규제는 별도 변수로 통제해야 한다.
- **과거 패턴이 미래를 보장하지 않는다.** 2006년 노량진뉴타운 지정기의 상승률을
  지금 구역에 그대로 적용할 수 없다.
- **거래가 적은 단지는 추정이 불안정하다.** 월 3건 미만 구간이 많은 소규모
  단지는 결과를 표시하지 않는 편이 낫다.
- 이 설계는 **서울 기준**이다. 경기·인천은 단계 이력 데이터 확보 난이도가 달라
  별도 검토가 필요하다.
