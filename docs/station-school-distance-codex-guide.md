# 역·학교 거리 전 단지 저장 작업 지침서

> 아래 수치와 문제 설명은 **작업 시작 당시 기록**이다. 현재 연결 방식은
> `AGENTS.md`의 `로컬과 운영의 수집 자료는 같은 원본을 사용` 원칙을 따른다.
> 로컬 자료는 `pipeline/shared_data.py`로 운영 원본을 자동으로 읽는다.
> 과거의 로컬 파일 수를 현재 수집 현황으로 인용하지 않는다.

## 1. 목표

서울·경기·인천 전 단지의 **역 거리와 학교 거리를 서버에 저장**한다.
어떤 경로로 리포트를 열어도 같은 거리와 같은 점수가 나오게 한다.

## 2. 왜 하는가

같은 단지인데 리포트마다 입지 항목이 다르게 나온다.

| 단지 | 단지 목록에서 연 리포트 | 새로 계산한 결과 |
|---|---|---|
| 신트리1단지 입지 점수 | 19.8 / 30 | 22.5 / 30 |
| 역 | 안 나옴 | 신정네거리역 2호선 · 직선 725m |
| 학교 | 안 나옴 | 서울남명초등학교 · 186m |

원인은 다음과 같다.

1. `pipeline/budget_candidates.py`는 목록을 만들 때 저장된 역 거리만 쓰고, 없어도 카카오를 호출하지 않는다.
2. 학교 거리는 단지 좌표가 필요한데, 좌표가 역 거리 캐시에 같이 저장돼 있다. 그래서 역 거리가 없으면 학교도 `no_coordinates`가 된다.
3. 집픽 분석 보기를 눌러도 목록에서 만든 점수를 그대로 쓴다. `refreshLocationScoreSheet`는 점수표를 열 때와 비교 화면에서만 돈다.
4. 역과 학교가 다 비면 `zippickDemandScoreReason`이 가격 순위 문구("지역 후보 1/3위 · 중상위권 가격")를 대신 보여준다.

## 3. 작업 시작 당시 상태 (2026-10-31, 로컬 기준)

- 전체 단지: `real_estate_search.APARTMENT_MASTER` 20,006곳
- 역 거리 없음: 19,788곳 (서울 9,056 · 경기 8,453 · 인천 2,263 · 지역 없음 16)
- 지역 없음 16곳은 주소가 없고 `unsupported_region`이다. 값을 만들지 말고 그대로 둔다.
- 학교 저장 기록: 650곳
- **운영 서버 수치는 확인하지 못했다.** T0에서 먼저 잰다.

| | 역 거리 | 학교 거리 |
|---|---|---|
| 코드 | `pipeline/kakao_station_distances.py` | `pipeline/education_environment.py` |
| 저장 위치 | `pipeline/cache/apartment_station_distances.json` | `data/education_environment_seoul_gyeonggi.json` |
| 배포 후 | 유지됨 (`shared/cache` 심볼릭 링크) | **서버에서 새로 저장한 값이 지워짐** (릴리스 폴더 안) |
| 일괄 도구 | 있음 (`--all`) | 없음 |

## 4. 지켜야 할 규칙

- `AGENTS.md`를 먼저 읽고 따른다. 특히 문구 원칙, 판단 제목 원칙, 배포 순서를 지킨다.
- 실제 자료가 없으면 거리를 만들지 않는다. 추정값이나 구 평균으로 채우지 않는다.
- 단지 식별은 `kakao_station_distances.entity_id`와 `apartmentId`를 쓴다. 단지명만으로 매핑하지 않는다.
- **호출 실패를 "자료 없음"으로 저장하지 않는다.** 한도 초과, 인증 오류, 네트워크 오류는 저장하지 않고 다음 실행 때 다시 시도한다.
- API 키를 코드, 문서, 로그, 커밋에 넣지 않는다.
- 로컬 작업 폴더를 `scp`나 `rsync`로 서버에 복사하지 않는다.

## 5. 작업

### T0. 사전 확인 (읽기만)

1. `git status`를 확인한다. 이 문서 작성 시점에 커밋하지 않은 변경이 많고, 배포 스크립트는 변경이 남아 있으면 멈춘다.
   - **남의 변경을 임의로 묶어 커밋하거나 되돌리지 않는다.** 정리 방법은 사용자에게 묻는다.
2. `deploy/exe-dev/zippick.service`에서 서버의 실행 경로와 파이썬 경로를 확인한다.
3. 서버에 카카오 REST 키가 설정돼 있는지 값을 출력하지 말고 확인한다.
4. 서버의 현재 저장 수와 디스크 여유를 잰다.
5. 카카오 로컬 API의 현재 일일 한도를 확인한다. 하루 10만 건쯤으로 알고 있지만 검증하지 않은 값이다.

호출량 추정은 역 거리 최대 약 4만 번(주소 1번 + 역 조회 1번, 타일 공유로 줄어듦), 학교 거리 최대 약 12만 번(학교·학원 각 최대 3페이지)이다.
한도를 넘으면 여러 날에 나눠 돌린다.

### T1. 역 거리 저장 (서버, 코드 변경 없음)

1. 실행 전 확인: 저장 도구와 운영 서비스가 같은 캐시 파일을 쓴다. `_merge_records`와 `_file_revision`이 동시 쓰기를 안전하게 처리하는지 코드로 확인한다. 값이 덮어써질 수 있으면 먼저 알린다.
2. 호출 수만 확인한다.

   ```bash
   python pipeline/kakao_station_distances.py --all --dry-run
   ```

3. 20곳으로 시험하고 결과를 확인한다.

   ```bash
   python pipeline/kakao_station_distances.py --all --limit 20 --workers 2
   ```

4. 문제가 없으면 SSH가 끊겨도 계속 돌도록 `tmux` 등으로 전체를 실행한다. 작업자 수는 기본값 이하로 시작한다.

   ```bash
   python pipeline/kakao_station_distances.py --all
   ```

5. 저장한 단지는 건너뛰므로, 멈추면 같은 명령을 다시 실행한다. 끝난 뒤 `--retry-unavailable`로 못 찾은 단지를 한 번 더 확인한다.

서버 명령은 사용자가 이 작업을 승인한 뒤에 실행한다.

### T2. 학교 저장 위치 옮기기

배포해도 지워지지 않게 `pipeline/cache/`로 옮긴다.

1. 저장 위치를 `pipeline/cache/education_environment_records.json`으로 만든다.
2. `_load_dataset`은 기존 `data/...json`(구역·학교 기준 자료)과 새 저장 기록을 합쳐 읽는다. 같은 단지는 새 기록을 우선한다.
3. `_save_precomputed_record`는 새 파일에 쓴다. 지금처럼 기록 1건마다 전체 JSON을 다시 쓰면 2만 건에서 너무 느리다. 일괄 실행 때는 묶어서 저장한다.
4. 저장은 임시 파일을 쓴 뒤 교체한다. 서비스와 일괄 도구가 동시에 써도 기록이 사라지지 않게 한다.
5. `scoreFormulaVersion`을 함께 저장하고, 현재 버전과 다른 기록의 처리 방식은 기존 동작과 맞춘다.
6. `data/...json`에는 로컬에서 쌓인 커밋 안 된 기록이 있다. 이 파일을 어떻게 처리할지 사용자에게 묻고, 임의로 되돌리지 않는다.

### T3. 학교 일괄 저장 도구

`pipeline/education_environment.py`에 역 거리 도구와 같은 사용법의 명령을 만든다.

```bash
python pipeline/education_environment.py --all --dry-run
python pipeline/education_environment.py --all --limit 20 --workers 2
python pipeline/education_environment.py --sido 서울특별시 --sigungu 양천구
python pipeline/education_environment.py --all --retry-unavailable
```

- 이미 점수가 있거나 구역 자료로 계산되는 단지는 호출하지 않는다.
- 좌표가 없으면 호출하지 않고 `no_coordinates`로 집계한다. 그래서 **T1이 끝난 뒤 실행한다.**
- 지금 `education_environment_for_entity`는 `_score_from_nearby_places`의 모든 예외를 삼킨다. 일괄 도구는 한도 초과와 인증 오류를 구분해 **즉시 멈추고**, 그때까지의 결과를 저장한다.
- 끝나면 저장, 건너뜀, 좌표 없음, 학교 없음, 실패 수를 JSON으로 출력한다.

### T4. 리포트를 열 때 비어 있는 점수 다시 계산

저장 후에도 새 단지나 조회 실패 단지가 있을 수 있어 필요하다.

1. 집픽 분석 보기를 열 때 `locationScoreNeedsRefresh(item)`가 참이면 `refreshLocationScoreSheet(item)`를 호출하고, 응답 후 리포트를 다시 그린다.
2. 같은 단지의 목록 카드 점수도 같은 값으로 바뀌는지 확인한다.
3. 리포트 열기가 재계산 때문에 막히면 안 된다. 먼저 화면을 보여주고 값이 오면 바꾼다.
4. 단지명 변형도 확인한다. 로컬에서 `/api/apartment-report`를 `name=신트리1단지&region=양천구&legal_dong=신정동`으로 부르면 역·학교가 모두 비고 입지 점수가 14.4로 나왔다. `name=신트리1단지아파트&region=서울특별시 양천구&legal_dong=신정동&jibun=1259`로 부르면 정상이었다. 실제 화면에서도 이런 값이 넘어가는지 확인하고, 그렇다면 식별 기준에 맞게 고친다.

### T5. 입지 문구 고치기

`앱화면/real-estate-search.html`의 `zippickDemandScoreReason`을 고친다.

1. 역과 학교가 모두 없으면 가격 순위 문구를 쓰지 않는다.
   `역·학교 자료를 불러오지 못해 판단할 수 없어요`
2. 지금은 자료가 있기만 하면 거리와 상관없이 "역과 학교가 가까워 유리해요"라고 쓴다. 항목 점수를 기준으로 나눠 쓴다.
   - 좋음: `역과 학교가 가까워 출퇴근·통학에 유리해요`
   - 보통: 거리만 사실대로 쓰고 가깝다고 하지 않는다. 예: `신정네거리역까지 직선 725m, 서울남명초등학교까지 186m예요`
   - 나쁨: `역이 멀어 출퇴근에는 불리해요`처럼 약한 항목을 말한다.
   - 한쪽 자료만 없음: 있는 쪽만 판단하고 없는 쪽은 `자료가 없어요`라고 구분한다.
3. 거리는 직선거리다. `직선`을 빼거나 도보 시간처럼 쓰지 않는다.
4. 제목과 강조 문장을 `확인하세요`로 끝내지 않는다.

### T6. 테스트

- 관련 테스트를 고치고 추가한다: `tests/test_kakao_station_distances.py`, `tests/test_report_price_check.py`, `tests/test_frontend_apartment_search.py`
- 다음 경우를 새로 시험한다.
  - 저장 기록과 기준 자료를 합쳐 읽는다.
  - 한도 초과 때 실패가 저장되지 않고 도구가 멈춘다.
  - 다시 실행하면 저장된 단지를 건너뛴다.
  - 입지 문구의 좋음·보통·나쁨·자료 부족 네 경우.
- 실행 방법:

  ```bash
  PYTHONPATH=pipeline .venv/bin/python -m unittest discover -s tests
  ```

- `test_paid_report`의 2개 테스트는 이 작업과 무관하게 이미 실패한 적이 있다. 새로 생긴 실패와 구분해서 보고한다.

### T7. 배포와 학교 저장

1. 이 작업의 변경만 골라 커밋한다.
2. `AGENTS.md`의 exe.dev 배포 순서를 그대로 따른다. `git push origin main` 후 `./scripts/deploy-exe-dev.sh`를 실행한다.
3. 배포 때 `설정.txt`의 대기 중인 키도 확인한다. 한국부동산원키는 로컬에만 있어 추가가 필요하다. 나이스키는 NEIS 기능을 배포할 때 추가한다.
4. 서버에서 T3 도구를 시험 실행한 뒤 전체를 실행한다.
5. 끝난 뒤 다시 배포해 보고 저장 수가 줄지 않는지 확인한다.

## 6. 완료 기준

- [ ] 서버의 역 거리 저장 수가 지역 없음 16곳을 뺀 단지 수에 가깝다. 남은 단지는 사유별 수를 보고한다.
- [ ] 서버의 학교 점수 저장 수를 같은 방식으로 보고한다.
- [ ] 다시 배포해도 저장 수가 그대로다.
- [ ] 신트리1단지(양천구 신정동 1259)가 단지 목록과 직접 검색 어느 쪽에서 열어도 같은 역, 같은 학교, 같은 입지 점수로 나온다. 신정네거리역 2호선 725m, 서울남명초등학교 186m가 기대값이다.
- [ ] 저장 전에 비어 있던 단지 3곳 이상을 운영 서버 화면에서 확인한다. 서울, 경기, 인천을 하나씩 고른다.
- [ ] 입지 항목에 가격 순위 문구가 나오지 않는다.
- [ ] 모바일 폭과 데스크톱 폭에서 리포트가 정상으로 보인다.

## 7. 사용자에게 보고할 내용

1. 저장 결과: 역, 학교 각각 저장, 실패, 남은 단지 수
2. 카카오 호출 수와 며칠 걸렸는지
3. 실제 화면에서 확인한 단지 목록
4. 하지 못한 일, 확인하지 못한 일
5. 정기 갱신 방법: 새 역이 생기면 저장값이 낡으므로 몇 달에 한 번 다시 돌리는 절차
